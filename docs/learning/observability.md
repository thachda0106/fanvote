## 1. Trace the synchronous request (gateway → voting → Postgres)

```
k6/curl  ──HTTP──▶  Envoy (Gateway API)  ──HTTP──▶  voting (NestJS)  ──pg──▶  Postgres
 traceparent          ingress + router              POST /api/v1/events/:id/votes
 (e2e injects)        spans (component=proxy)       pg.query:{BEGIN,INSERT,COMMIT}
```

Verified in Jaeger (`kubectl -n eventista port-forward svc/jaeger 16686:16686`):

- Service names: `eventista.eventista` (Envoy), `voting`, `identity`,
  `analytics`.
- `scripts/e2e.sh` sends an explicit
  `traceparent: 00-<trace-id>-<span-id>-01`; Envoy continues that trace
  (tracing is configured at 100% on the `EnvoyProxy`,
  `deploy/helm/eventista/templates/gateway.yaml`).
- Voting's spans: server span → Nest internal spans → `pg.query:*` client
  spans (auto-instrumentation, `@opentelemetry/auto-instrumentations-node`).
- The identity hop inside the same trace is the **JWKS fetch** performed by
  voting's local verifier (`services/voting/src/auth/jwt-verifier.service.ts`);
  it joins the trace because jwks-rsa uses the instrumented HTTP client.

**Why the DB span matters:** it proves the trace reaches the datastore, not
just the process boundary. The e2e assertion accepts `pg.*` operation names
and `db.system` tags (`scripts/e2e.sh`).

## 2. Trace the asynchronous request (vote → outbox → Kafka → analytics)

```
HTTP vote tx (PG)                relay (100 ms poll)                 analytics consumer
BEGIN                              UPDATE…RETURNING claim              extract(traceparent)
INSERT ballot_stub                 start PRODUCER span                 CONSUMER span
INSERT outbox (payload,            context.with(producer span, send)   upsert Mongo _id = message id
  traceparent, request_id)         KafkaJS span joins same trace       manual commit after upsert
COMMIT                           inject traceparent + AsyncAPI hdrs
```

Key code:

- Claim-then-send, never commit-then-send:
  `services/voting/src/outbox/outbox.relay.ts:99` (`FOR UPDATE SKIP LOCKED`,
  `attempts < 10`, stale-claim re-claim).
- Producer context: `publishRow` extracts the stored `traceparent`, starts
  the producer span, and runs the Kafka send **inside `context.with(...)`**
  (`outbox.relay.ts:151`). This is the fix for the split-trace defect:
  KafkaJS auto-instrumentation used to start a root trace and overwrite the
  injected header — the consumer then linked to the wrong trace.
- Headers now match `contracts/asyncapi.yaml` `commonHeaders`
  (`id, type, occurredAt, producer, aggregateId, aggregateType, traceparent,
  correlationId`), not CloudEvents `ce_*`.
- Consumer: `services/analytics/app/consumers/vote_cast.py` extracts the
  parent context, upserts `_id = message id` (B6), commits only after the
  write. A failed record re-raises so the supervisor restarts from the last
  committed offset (at-least-once, no loss).

**Proven by e2e:** the analytics span is in the SAME trace id as the vote
request; `make e2e` fails if the consumer span is missing.

## 3. Correlation and logs

- `x-request-id` is accepted or generated by every service and echoed;
  Envoy may generate one when absent.
- Log lines (pino / logstash-logback / structlog) carry
  `service`, `request_id`, `trace_id`, `span_id`, `route`, `status`,
  `duration_ms`.
- Join one request across languages by `request_id`; join the async leg by
  `trace_id`.

## 4. Metrics, health, errors (the T1.6 checklist)

- `/metrics` is Prometheus text on every service; RED series use bounded
  labels only (route template + status class — never event/user ids).
- `/healthz` is datastore-independent; `/readyz` returns 503 when a real
  dependency is down (voting: PG ping; analytics: Mongo ping + consumer
  state; the mock IdP and commerce are stateless in Phase 1).
- `/metrics` and the health endpoints are **not** exposed through the
  gateway (Q-22); e2e reaches them via port-forward.
- Errors use `{code, message, requestId}` with `VALIDATION_FAILED` (400),
  `UNAUTHORIZED` (401), `NOT_FOUND` (404), `DEPENDENCY_UNAVAILABLE` (503),
  `INTERNAL_ERROR` (500).
- Outbox backlog gauge refreshes every 5 s even while the relay is paused
  (otherwise a paused relay reports zero backlog).

## 5. Why the mock IdP is not a shortcut (T1.3)

- It generates a real RS256 keypair on boot, publishes a real JWKS
  (`kid` = RFC 7638-style thumbprint of the public key), and signs tokens
  with the same `iss`, `aud`, `sub`, `roles`, `exp`, `jti` claims the Phase 4
  issuer will use (`services/identity/src/auth/jwt-keys.service.ts`).
- Verification is identical: Envoy `SecurityPolicy` fetches the JWKS
  (`remoteJWKS.uri`), and every service verifies locally via cached JWKS
  with refresh-on-unknown-`kid` — rotation-safe, no identity hop on the hot
  path. Only the OAuth dance is missing.
- Therefore Phase 4 replaces **who mints and distributes** tokens, not **how
  they are verified**. Forged signatures are rejected at the edge (401,
  proven by smoke) and again inside the service (defense in depth).

## 6. Failure modes seen (and where they are documented)

| Symptom | Cause | Fix |
|---|---|---|
| Relay crashed every 100 ms, `undefined.connect` | `OutboxRelay` lacked `@Injectable()` and injected raw `Pool` | constructor takes `DbService`; decorator added |
| Kafka consumer in a different trace | KafkaJS instrumentation started a root span and overwrote `traceparent` | send inside `context.with(producer span)` |
| `make smoke` 429s in the smoke scenario | burst scenario overlapped the 10 s smoke run | burst starts at 15 s |
| `make e2e` "passed" without trace spans | shell `done \|\| fail` checked `sleep`, not the assertion | explicit `TRACE_OK` flag |
| One 401 on the first vote after a control-plane restart | JWKS cold-fetch failed (fail-closed) | retry/diagnose; documented as an accepted Phase 1 behavior |
| Host :8080 blackholed after container recreate | Docker Desktop port proxy not re-registered | restart the control-plane container |

## 7. Known gaps / risks (do not claim these are verified)

- Expired-token rejection at the edge is not exercised in e2e (only forged
  tokens); Envoy's standard expiry check is assumed, not tested.
- Rate limits are Envoy **local** buckets: N replicas = N × limit. Phase 4
  decides global limits if needed.
- The mock IdP generates a keypair per process; multiple identity replicas
  would serve different keys. Single replica is a Phase 1 constraint
  (Phase 4 replaces it).
- The analytics supervisor restarts on a poisoned record; the same offset is
  redelivered. A DLQ is Phase 5 scope.
- Local cluster memory: Docker Desktop is ~5.8 GiB here; the plan floor is
  16 GB. The stack fits only because commerce is DB-less in Phase 1.
